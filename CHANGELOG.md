# Changelog

Notable changes to plugins in this marketplace, grouped by plugin. Versions follow [Semantic Versioning](https://semver.org/) and match each plugin's `.claude-plugin/plugin.json` / `.codex-plugin/plugin.json` `version` field.

## meta-ads

### 1.0.0 — 2026-08-23

- New plugin. Meta (Facebook/Instagram) advertising through both of Meta's own ads AI connectors: the hosted MCP server at `https://mcp.facebook.com/ads`, bundled as a real server declaration in `plugins/meta-ads/.mcp.json`, and the official ads-cli (`meta`, PyPI `meta-ads` v1.1.0) behind `scripts/meta_ads.py`
- Kept both paths rather than picking one, because neither is a superset. The hosted server has tools with no CLI equivalent at all — benchmarks and opportunity signals, Business Help Center article search, the account activity log — while the CLI reaches flags no tool exposes: DCO asset feeds (`--images`/`--titles`/`--bodies`), raw `--targeting`/`--promoted-object`/`--asset-feed-spec` JSON, EU DSA payor/beneficiary fields, and `--fields` as an escape hatch to any Marketing API field
- The hosted server's OAuth was verified against the live endpoint rather than taken from docs: public client, PKCE `S256`, `authorization_code` + `refresh_token`, dynamic client registration at `https://mcp.facebook.com/.well-known/register/ads`, authorize via `https://www.facebook.com/v26.0/dialog/oauth`. So there is genuinely no Meta app to create and no client ID to configure for that path. `oauth.scopes` is pinned in `.mcp.json` to exactly the set the server's own `WWW-Authenticate` header advertises — pinning changes nothing about the grant, it just puts it in the repo where it can be narrowed; `reference/mcp.md` documents the read-only subset
- Tool names are deliberately not enumerated anywhere in the skill. Meta's overview documents seven areas, not a roster; the "29 tools" figure and the tool names in circulation are third-party and have already moved once, so `SKILL.md` says to read the live tool list instead
- **`meta auth status` cannot be used as verification, and the skill says so twice.** It prints `Authenticated (token: ****)` and exits 0 for any non-empty string — `ACCESS_TOKEN=bogus` passes. It checks presence, never validity, and never calls the API. `meta_ads.py check` calls `adaccount list` for real, exits non-zero when the token is rejected, and exits non-zero again when the token is valid but cannot reach the `--account` that was named
- **`.env` is read from any ancestor directory**, verified from a subdirectory two levels down. An `ACCESS_TOKEN` there decides which advertiser's money a write spends, based on nothing but the working directory. The wrapper always sets the child's `ACCESS_TOKEN`/`AD_ACCOUNT_ID`/`BUSINESS_ID` explicitly and prints the file it ignored — an empty environment variable beats `.env` just as a populated one does, which is what makes blanking them work
- Env var is `META_ADS_ACCESS_TOKEN`, remapped to the CLI's `ACCESS_TOKEN` for the subprocess only — same reasoning as `ga4`'s `GA_SERVICE_ACCOUNT_KEY`, but more urgent here: `ACCESS_TOKEN` is generic enough to collide with almost anything else on the machine
- Following `gtm`/`gsc`/`ga4` 2.0.0: no env var for the ad account. `--account act_...` is required on every account-scoped command, exempting only `ads adaccount` and `ads page`, which are system-user-scoped. An ad account is one advertiser's money, so it belongs to the task, not the machine
- Found while testing, and the reason `--account` is a wrapper-owned flag rather than a passthrough: `--ad-account-id` and `--business-id` are options of the CLI's `ads` **group**, so `ads campaign list --ad-account-id act_1` fails with `No such option` — the CLI's own form is `ads --business-id 123 catalog list`. Worse, `dataset connect`/`dataset disconnect` reuse `--ad-account-id` as a *leaf* option with a different meaning ("the account to connect the dataset to"), so a wrapper that hoisted every occurrence would silently break those two. `--account`/`--business` are distinct names (verified absent from all 72 commands) routed through the child environment, leaving the CLI's own flags untouched
- Every `create`/`update`/`delete`/`connect`/`disconnect`/`assign-user` through the wrapper appends to a gitignored `.meta-ads-audit.jsonl` at the repo root, with the redacted argv, the account, and the exit code. Stated as a limitation rather than papered over: **writes through the MCP tools do not land there** — Meta's account activity log is the trail for those, and the server's activity-log tool is how to read it
- The CLI's own `--help` confirms every create defaults to `--status PAUSED`, and the skill forbids bundling activation into a create. The hosted server is documented as creating paused entities too, but that is unverified here, so the skill tells the reader to check the returned status on their first create through it rather than assuming it. `ARCHIVED` is documented as the reversible answer to "stop this", against `delete`, which cascades a campaign's ad sets and ads
- Documented the budget trap the CLI's own help only half-covers: budgets are bare integers in the account currency's smallest unit, and the help text's "cents" is a USD assumption. On a currency whose smallest unit is the whole unit the same `--daily-budget 5000` is 100× off. The skill requires reading the account currency before quoting or setting any budget
- Exit codes mapped by running them: 0 success — **and also `auth status` with no credentials at all**; 1 an unhandled traceback (it fails creating `~/.config/meta/` before checking anything); 2 usage, e.g. `No ad account configured`; 4 API error, e.g. `API error (190)`
- Zero-install by default: `uvx --from meta-ads meta`, verified working on Python 3.12.3. `META_ADS_CLI` overrides, a `meta` on `PATH` is preferred when present
- The package ships compiled `.so` modules with no readable `.py`, so `--help` is the only source of truth for flags — and a rich one, carrying the CBO/ABO/flex budget rules and the full campaign → ad set → creative → ad sequence inline. `reference/cli.md` covers the command map, the decision tables, and the traps `--help` doesn't mention, and tells the reader to run the leaf `--help` before composing any write rather than duplicating 2,000 lines of it
- `reference/setup.md` carries a "Finding the IDs" section for all four — ad account, business, Page, pixel — because the business ID in particular has no CLI answer at all: `adaccount get`/`list` take no `--fields`, so the account's `business` field is unreachable from the CLI and it has to come from Business Settings or a direct Graph call
- `reference/setup.md` documents the `debug_token` self-inspection call, because it answers "the token is valid but sees nothing" in one request. The distinction that matters is inside `granular_scopes`: a scope listed there with **no `target_ids`** means the permission was granted but no asset was ever attached, which presents as a valid token returning `{"data": []}` from `/me/adaccounts` — an assignment problem, not a token problem, and the two have completely different fixes
- **`ads page list` returns a live Page access token in its default field set** — found by running it against a real Page. Any transcript, CI log, or pasted snippet of that output carries a working credential that can post as the Page, and it stays valid until the parent system user token is revoked. `SKILL.md` forbids echoing that output raw and `reference/cli.md` carries a filter to strip it
- **Verified live against a real ad account** with a system user token carrying seven scopes: `check`, `campaign list`, `insights get`, `page list`, `catalog list`, `dataset list`, and `guidance list` all returned real responses, and the empty ones (`No results.`, `{"data":[]}`) confirmed the empty-is-a-finding behaviour on a fresh account rather than an error. `check`'s two failure branches both fired for real on the way there — a rejected token, and a valid token that could not reach the named account. The `--business` requirement for `page`/`catalog`/`dataset` was found this way too, as was the Page access token in `page list` output
- The credential-resolution behaviours (`.env` precedence up the directory tree, the `auth status` false positive, exit codes, every wrapper guardrail) were verified earlier against the real binary with invalid credentials, which exercises them without needing an account
- **Still unverified, and flagged as such in `SKILL.md`:** the write path. No `create`/`update`/`delete` has been run against a live account, so the audit log has only ever recorded a failing call (exit 4), never a successful one. And the hosted MCP server end to end — its OAuth consent flow and its actual tool list both need a completed browser grant, which is why `SKILL.md` says to read the tool list rather than trusting any published roster
- `read_insights` turned out not to be offered by the app used for the token, because the available scope list depends on the app's configured use cases. It is not in the seven the skill asks for by accident — ad-account-level insights are covered by `ads_read`; `read_insights` only matters for Page-level insights, and adding it needs a use case added to the app first

## ga4

### 2.0.0 — 2026-08-20

- **Breaking: the ID flags no longer fall back to an environment variable.** `--property` is now required on every command that takes it. An ID like this identifies one site, so it belongs to the task, not to the machine: exported globally it follows you into every unrelated project, and a `create`/`patch`/`archive` could land on whatever property happened to be exported — with nothing in the command naming the target. The service account key stays in the environment, because that genuinely is a property of this machine. `GA_PROJECT_ID` also stays: it names the GCP project billed for API quota, which travels with the key rather than with any GA4 property
- `analytics-mcp`'s reporting tools were never affected — they have always taken `property_id` as a call argument
- `mcp_client.py` now exits non-zero when the call fails, which it previously never did for the failure that matters most. Detecting that needs two checks, not one: `analytics-mcp` reports a schema violation with `isError: true`, but swallows anything raised *inside* a tool — a missing credentials file, an unknown tool name — and returns it as ordinary text content with **`isError: false`** and a `{"error": "..."}` body. Found live: a broken credentials path printed its error to stdout and exited 0, so every caller checking exit status read it as success. The `{"error": ...}` match is narrowed to a dict of exactly one string-valued `error` key, so a real report carrying an `error` field is never misread as a failure
- `mcp_client.py` also: expands `~` in `GA_SERVICE_ACCOUNT_KEY` before handing it to the subprocess (the three stdlib scripts already called `Path.expanduser()`; `analytics-mcp` is a separate process and never did, so a tilde path worked everywhere except here), treats an exported-but-empty var as unset, checks the key file exists up front, surfaces the subprocess's stderr instead of discarding it when no response arrives, and kills a hung server rather than raising `TimeoutExpired` as a traceback
- Failure output now goes to stderr and success to stdout, so the two can be told apart without parsing
- Unchanged and worth stating: the registered MCP server in `.mcp.json` gets none of this — Claude Code launches it directly, so its `GA_SERVICE_ACCOUNT_KEY` must already be an absolute path *and* be visible to a non-interactive process (`~/.zshenv`, not `~/.zshrc`), and it only picks up either at the start of a fresh session
- `README.md` still advertised the removed `GTM_ACCOUNT_ID`/`GTM_CONTAINER_ID`/`GTM_WORKSPACE_ID`, `GSC_SITE_URL`, and `GA_PROPERTY_ID` env vars after the SKILL.md files had dropped them — the marketplace README contradicted all three skills until now
- Migration: drop `GA_PROPERTY_ID` from your shell profile and pass `--property` explicitly. A command that relied on the fallback now fails with `error: the following arguments are required`, loudly and before any API call — it cannot silently hit the wrong property
